# isudo for iPhone

The approver's side of isudo: it shows exactly what a paired computer wants
to run as root, and signs an approval with a Secure Enclave key behind
Face ID.

- `IsudoKit/` is the logic, with no UI: decoding and checking requests,
  pairing, the display rules, the relay client and the signing keys. It is a
  Swift port of `crates/phone` and `crates/proto`, and its tests check it
  against vectors generated by the Rust code (`testdata/vectors.json`).
- `App/` is the SwiftUI app.
- `project.yml` is the Xcode project, generated with XcodeGen.

## Build and test

```sh
(cd IsudoKit && swift test)   # logic, on the Mac
./build.sh                    # app, for the Simulator (warnings are errors)
./screenshots.sh /tmp/shots   # sample screens, light and dark
./e2e.sh                      # Simulator app + local relay + development isudo
```

`e2e.sh` needs the Rust binaries in `../target/debug`, including a
development build of isudo copied to `isudo-dev`
(`cargo build -p isudo --features dev-unprivileged`).

## Running on a phone

```sh
cp Local.xcconfig.example Local.xcconfig     # then edit it
xcodegen generate
open Isudo.xcodeproj
```

`Local.xcconfig` holds your Apple developer team id and a bundle identifier
you own; it is not tracked by git. Pick your phone as the run destination
and press Run. Xcode creates the signing certificate and profile for you.
The phone needs Developer Mode on, and Face ID or Touch ID set up.

Push notifications need a paid developer membership and an APNs key
configured on the relay (`ISUDO_APNS_*`, with `ISUDO_APNS_TOPIC` equal to
your bundle identifier); without push the app still shows requests while it
is open. On a free account, remove the two entitlements from `project.yml`
or signing will fail.

The app icon is drawn by `tools/make-icon.swift`.

## Apple Watch

`Watch/` is the watch app. It is embedded in the phone app, so installing
the phone app on a phone with a paired watch installs it too; its bundle
identifier is yours with `.watch` on the end. To run it alone in a watch
Simulator, use the `IsudoWatch` scheme. It takes the same `-fixture`
argument (`simple`, `longer`, `phone-only`, `approved`, `status`, `empty`).

To use it:

1. On the computer: `sudo isudo-admin watch on`.
2. Open isudo on the watch and leave it open.
3. On the phone: open the computer's page in isudo, tap Allow Apple Watch,
   and confirm with Face ID.

The watch needs a passcode, with wrist detection on. Its key is made in its
Secure Enclave, exists only while the watch has a passcode, and signs only
when the system says the watch has stayed on the wrist since it was
unlocked.

What the watch does is in `IsudoKit` (`Delegation.swift`,
`WatchMessage.swift`) and tested there against the Rust reference: the
format of the phone's authorisation, the rule for what a watch may approve,
every check before a request is shown, and the messages between phone and
watch.

`./e2e-watch.sh` runs the whole thing in a phone Simulator and its paired
watch Simulator, against a local relay and a development build of isudo:
the phone authorises the watch, the watch approves one request by holding
its button and denies another that only the phone could approve.

**Tried on one real watch** (an Apple Watch Series 12 on watchOS 27, with
an iPhone 16 Pro, installed through TestFlight). These six checks all did
what they should:

| Check | Expected |
|---|---|
| A simple request with the watch app open | The terminal says "or its watch"; holding the button on the watch runs it |
| A request that names a variable | The watch says "Review on iPhone" and can deny it, with a reason the caller sees |
| A request with the app closed and the phone locked | A notification on the wrist |
| A request while the phone is in use | It appears on the phone and the wrist stays quiet |
| Approving with the watch taken off | It refuses to sign |
| After `sudo isudo-admin watch off` | The watch is sent nothing and the phone carries on |

That is one watch, one phone and one relay. Where watchOS might behave
differently elsewhere, the app has somewhere to fall back to:

| If this does not work | Then |
|---|---|
| Approving from inside the notification | Tapping the notification opens the app on the same request |
| The pushed notification carrying the sealed request | The app fetches it from the relay when opened |
| The watch reaching the relay itself, as on a private network | Answers go through the phone, which only carries them; the watch must be near the phone |
| Clearing the notification on the phone clearing it on the watch | The phone also tells the watch directly; a stale notification shows the request as expired or answered |

### Getting it onto a watch

Running the `Isudo` scheme from Xcode installs the watch app too, if Xcode
can reach the watch: it must be listed in Xcode's devices window, which is
also what makes the Developer Mode switch appear on the watch. If Xcode
never finds the watch (it can fail to, for no reason it will give), use
TestFlight, which needs neither:

```sh
./testflight.sh archive     # a release build of both apps, signed
./testflight.sh upload      # to App Store Connect
```

Create the app record for your bundle identifier in App Store Connect
first, add yourself to an internal testing group, and install from the
TestFlight app on the phone. A TestFlight build uses Apple's production
push service, so the relay's APNs key must allow production.

Away from the phone the watch gets no notifications in this version: they
are mirrored from the phone.

In the Simulator the signing key is a software key, because the Simulator
cannot make Secure Enclave keys bound to biometry. The app says so wherever
that pairing is shown. Device builds do not contain the software key at all:
on a phone without Face ID or Touch ID set up, pairing is refused.

Debug builds accept `-fixture NAME` (`empty`, `quiet`, `plain`, `risky`,
`long`, `multi`, `simulator`, `scan`, `confirm`, `confirmlink`, `waiting`,
`code`, `claimed`, `otherphone`, `steered`, `paired`) and
`-appearance light|dark` to show sample data. Sample data cannot be signed
or sent anywhere.
